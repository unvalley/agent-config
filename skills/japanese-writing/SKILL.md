# 日本語を書く

一般的な「整った日本語」を押しつけず、ユーザーの目的に沿って書く。unvalley のブログの文体は、そっくり真似るものではなく、デフォルトとして扱う。

## 依頼を整理する

次の順で適用する。

1. ユーザーが求める意味、制約、文体、形式に従う。
2. 提供された下書き、文例、掲載先、スタイルガイドに合わせる。
3. 原文のジャンル、読者、定着した用語を尊重する。
4. 上位の条件で決まらない部分だけ、このスキルのデフォルトを適用する。

原文から不足する文脈を推測する。編集では依頼を満たす最小限の変更にとどめる。下書きでは、文章を完成させるために不足する事実を作らない。

## 作業モードを選ぶ

- **コピーエディット**: 内容と声を保ち、文法、曖昧さ、冗長さ、表記、流れを直す。
- **リライト**: 必要に応じて構成を変えつつ、すべての主張とその強さを保つ。
- **ドラフト**: 調査や創作的な拡張が許可されていない限り、ユーザーのメモを事実の閉じた集合として扱う。もっともらしい例、動機、機能、実装詳細で埋めず、重要な不足を示す。
- **文体合わせ**: 提供された文例から局所的なルールを導く。文例で決まらない選択にだけ unvalley のデフォルトを使う。
- **ファクトチェック**: 依頼に調査または検証が明記されている場合だけ主張を確認する。確認済みの事実、解釈、未解決の問いを分ける。

## 意味と根拠を保つ

- ユーザーが変更を求めない限り、すべての主張、名前、数値、日付、引用、出典、リンク、技術用語、製品名、固有名詞を保つ。
- 確実性、不確実性、帰属、因果関係、時系列、否定、範囲を保つ。`可能性がある` を `〜だ` に変えたり、相関を因果に変えたり、個人の経験を普遍的なルールに変えたりしない。
- 事実、出典、引用、名指しされていない権威、経歴、動機、含意を作らない。
- 一般的なメモを、書かれていない具体性へ膨らませない。たとえば入力が特定の書式機能を挙げていない限り `rich formatting` は一般的なままにし、復旧動作を定義していない限り `conflict recovery` も一般的なままにする。
- `〜でした`、`〜と思います`、`おそらく`、`〜かもしれません`、または検証が必要だという明記によって、観測事実、推測、意見、記憶の境界を見えるようにする。
- 作者の声を担う意図的なユーモア、率直さ、ためらい、不均一なリズム、具体的な細部を保つ。

## 自然な日本語を書く

- 英語の構文を直訳せず、日本語の書き手が実際に使う表現を選ぶ。日本語の文脈上不要な主語や代名詞は省く。
- 原文の主な文体に合わせる。すべてを機械的に `です・ます` または `だ・である` に変えず、関係上不要な敬語も加えない。
- 直接的な動詞と具体的な名詞を使う。不要な名詞化、重複する結論、考えを前に進めない接続表現を削る。
- 意義を大げさにする表現、一般的な称賛、修辞疑問、整いすぎた三点セット、導入を繰り返すだけの結論など、定型的な AI 文体を避ける。`〜と言えるでしょう`、`〜ではないでしょうか`、`重要な役割を果たします`、`多岐にわたります` などは、禁止語ではなく点検するサインとして扱う。
- 変化をつけるためだけに、普通の言葉を堅い同義語へ置き換えない。主題が明確になるなら、同じ語を繰り返してよい。
- 理解を妨げる不統一がない限り、定着した漢字、かな、句読点、大文字・小文字、空白の選択を保つ。識別子、コマンド、コード、製品名は原形のままにする。

## デフォルトでは unvalley のブログの文体を使う

ユーザーがより強い文体指定をしない場合は、作者の公開ブログから導いた次のデフォルトを使う。

- 冒頭の1〜2段落で、何を扱う文章なのか、なぜ書くのかを示す。広い社会的トレンドや儀礼的な前置きから始めない。
- 段落を短くし、一つの点に集中させる。具体的な観察、例、数値、リンク、コード、実際の結果で説明する。
- 文学的な磨き上げより、無理のない会話的な明快さを優先する。悪い結果、不確実性、トレードオフ、個人的な好みを率直に書く。
- 個人的な文章で一人称が必要なら `自分` を使う。中立的なドキュメントに一人称の語り手を足さず、提供された下書きが `私`、`僕`、または主語なしなら無理に `自分` へ変えない。
- 長い記事では、主題や行動が明確になる説明的な見出しとリストを使う。短いメモに完全な記事構成を作らない。
- 訳すと不正確になる英語の技術用語、製品名、コミュニティ名は、馴染みのある形のままにする。
- 根拠が支える強さで助言する。自分で確かめた結論は直接書き、推測や一般化は弱める。
- 作者の現在の判断、次の行動、開いた問い、軽い提案で終える。大きな教訓、一般的な楽観、無理なまとめを避ける。

一つの記事にある偶然の癖を真似しない。誤字、文体の不統一、絵文字の頻度、英語の挿入、極端に率直な表現が一つの記事にあっても再現しない。

## ブログ記事・論考の形を整える

- タイトルで主題、用途、結論を直接示す。スローガンを解読しなくても読者が理解できるタイトルを選ぶ。
- 文章量に比例した構成にする。短い背景、有用な本題、必要に応じた観察や注意点、短い終わりで組み立てる。
- リスト、手順、比較、コマンド、参照リンクは、文章より一覧しやすい場所に置く。
- `はじめに` や `まとめ` の見出しを反射的に加えない。案内に役立つ場合や掲載形式に合う場合だけ使う。
- 短いメモを長い記事に水増ししない。有用な単位は数段落とリストだけでもよい。

## ファイルと構造化された内容を守る

- Markdown などの構造化ファイルを編集するときは、原則として文章だけを変更する。ユーザーが求めない限り、フロントマター、コードブロック、インラインコード、構造化データ、表、HTML や MDX の構造、参照識別子、リンク先を保つ。
- 見出し、リスト構造、リンクラベルなどの書式は、依頼に必要で意味を保てる場合だけ変更する。
- コミットメッセージは `git-commits`、プルリクエストのタイトルと説明は `github-pull-request` で差分を確認し、正確な内容を把握してからこのスキルで文章を整える。

## ワークフロー

1. 作業モードを決め、読者、目的、声、形式、変更してはいけない内容を特定する。
2. 原文または文例から局所的な文体を抽出し、必要な部分だけ unvalley のデフォルトに戻す。
3. 依頼を満たす最小限の深さでドラフトまたはリライトする。
4. 根拠のない主張、翻訳調の構文、定型的なつなぎ、過剰な結論、不要な反復を削る。
5. 原文またはメモと比較し、主張の欠落、確実性の変化、帰属、名前、数値、日付、出典、リンク、書式の変更がないか確認する。
6. メモから下書きする場合は、新しく加えた具体的な名詞、数値、行動、動機、例、実装詳細をすべて点検する。根拠がないものや、創作的な拡張として明示的に許可されていないものを削る。
7. 貼り付けられた文章には、解説や別案を求められない限り修正文だけを返す。ファイルを編集した場合は、求められない限り全文を貼らず、パス、範囲、検証結果を報告する。
